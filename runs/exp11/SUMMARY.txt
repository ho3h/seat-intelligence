KILL RULE (gain < 5x at depth 3): HIT. Depth-3 gain is 3.5x-4.8x against the same interpreter run per candidate (all 95%
CIs below 5) and 0.86x-1.11x against compiled candidates. The lazy Peano regime is worse (1.3-1.4x).

WHY. The shared work is real but small: sub-expression values and the interpreter's dispatch are computed once per tree
position instead of once per candidate, which is exactly what the interpreted baseline pays for (its gain tracks mean
expression size: 1, 2.9, 6.8 nodes). But every candidate's final value is still materialised as its own leaf of a SUP
tree: the root operator applied to two superposed children of N_{h-1} values builds N_{h-1}^2 leaves, and HVM has no
merging of equal values. The superposed cost floors at ~16-24 interactions per candidate for maps (~50 per 4-step fold),
which is what evaluating one small compiled expression costs. Scaling (small DSL, h1..h4): sup cost/candidate
164 -> 158 -> 40 -> 16 (converging to the floor); gain vs compiled 0.41 -> 0.14 -> 0.41 -> 1.33x, vs interpreted
0.52 -> 0.30 -> 1.55 -> 7.46x. It grows with depth, but only like expression SIZE (linear in nodes), not the exponential
growth that sharing across reconverging candidates would give, and depth 5 (3e12 candidates) is out of reach anyway.
Laziness does not rescue it: partial-value pruning skips sibling sub-searches, but each emitted Peano constructor is
distributed over the SUP tree, so the per-candidate cost rises (96-105 itrs).

The plain enumerator wins by 2-4 orders of magnitude in wall-clock, and its class counts give the exact number of ALL
solutions (matching the superposed survivor count in every map config), so superposition does not even win on
"all solutions at once". (Caveat: fold OE merges on a probe grid, unsound in general; here every reported solution
passes the real fold.)

VERDICT: CLEAN NEGATIVE again, now in the regime chosen to favour superposition. Superposed HVM4 search is exact, but
its advantage over evaluating the same candidates independently is the amortised interpreter (<=4.8x at depth 3, ~1x
against compiled candidates), and it loses to an observational-equivalence enumerator by 100-10,000x. The missing
ingredient is value merging (hash-consing on outputs), which HVM's SUP/DUP does not do. Superposition is not a Genome
search mechanism for this workload; keep HVM2 + a Python OE enumerator.
Part (4) (lowering to HVM2) was conditional on superposition being competitive, so it was not built. What a Genome pipeline
would use: OE enumerator finds e(x) or g(acc,x) on the task examples -> instantiate the verified map/fold skeleton word
with e in its operator slot (a few OPR nodes; the skeleton's list walker is already a corpus word) -> genome/verify on
fresh seeds -> keep as a new word. The search is outside the medium; the word is inside.
NEXT: if superposition is to be tried a third time, it must be on outputs that are merged: an HVM-level OE (SUP leaves
keyed by value) or a lambda/structure-synthesis task where lazy pruning cuts whole sub-searches (SupGen's regime,
e.g. collapse_supgen_mul), measured against the same OE enumerator from day one.
